# 3.2.2 Functions: chain

`chain` accepts new blocks, validates them, appends them to the active chain and updates the tip. It is the CRUD for
tip, headers and blocks. It has no business logic except validating headers and blocks and updating the tip when a block
is sequential. `chain` maintains the UTXO set of the active chain.

Decisions about which headers and blocks to fetch, which chain is active, and when the tip is rolled back belong to
[block-sync](3.2.3-block-sync.md).

## State

| State                                                            | Store, table           |
|------------------------------------------------------------------|------------------------|
| UTXO set                                                         | `chainstate`, `coins`  |
| Undo data per block                                              | `chainstate`, `undo`   |
| Active chain by height: block hash, block time, median time past | `chainstate`, `active` |
| Tip                                                              | `chainstate`, `meta`   |
| Valid headers with height, cumulative chain work                 | `headers`, `headers`   |
| Blocks                                                           | `blocks`, `blocks`     |

Stores and tables are specified in [3.5](3.5-logical-database.md).

**CHN-01** `chain` MUST keep the tip in the same store as the UTXO set (`chainstate`), so that every change of the UTXO
set and of the tip is one atomic write (STO-02).

## Genesis

**CHN-02** On first start `chain` MUST store the genesis header of the network in use in `headers` and the genesis
block in `blocks`, and set the tip to the genesis block at height 0, in the order of
[STO-11](3.5-logical-database.md#first-start).

**CHN-03** `chain` MUST NOT add the genesis coinbase output to the UTXO set, as Bitcoin Core.

## Validation

**CHN-04** `chain` MUST apply the consensus rules active at the height of the header or block on the network in use
(`main`, `testnet4`, `signet`, `regtest`), with the deployment heights of rust-bitcoin's network parameters [R15].

### Headers

**CHN-05** `chain` MUST validate a header as Bitcoin Core's `CheckBlockHeader` and `ContextualCheckBlockHeader`:

- proof of work: the header hash is at most the target encoded in `bits`;
- `bits` equals the required target (`GetNextWorkRequired`);
- timestamp above the median time past of the previous 11 blocks and at most 2 hours in the future;
- version at least the minimum required after BIP34, BIP66 and BIP65.

**CHN-06** Contextual checks need the parent header. `chain` MUST validate a header only when its parent is a stored
header entry or an earlier header of the same `validate_headers` call.

### Blocks

**CHN-07** `chain` MUST validate a block as Bitcoin Core's `CheckBlock` and `ContextualCheckBlock`:

- merkle root, no duplicate transactions, size and weight limits, exactly one coinbase at position 0,
  `CheckTransaction` for every transaction, legacy sigop limit;
- transaction finality, BIP34 coinbase height, BIP141 witness commitment.

**CHN-08** `chain` MUST validate a block against the UTXO set as Bitcoin Core's `ConnectBlock`:

- BIP30: a transaction does not overwrite an unspent output (with Bitcoin Core's exceptions);
- `Consensus::CheckTxInputs`: inputs exist and are unspent, coinbase maturity (100 blocks), amounts in range, inputs
  cover outputs;
- BIP68 sequence locks, using the median time past stored in `active`;
- block sigop cost limit (80 000), counting P2SH and witness sigops;
- script verification of every input;
- coinbase outputs at most subsidy plus fees.

**CHN-09** Every rejection MUST carry Bitcoin Core's reject reason of the failed check (`high-hash`, `bad-diffbits`,
`bad-txnmrklroot`, `bad-txns-inputs-missingorspent`, `bad-cb-amount`, etc.).

## Interface

Direct calls. In v0.1 the only caller is `block-sync`.

**CHN-10** `chain` MUST execute calls that write one at a time.

### Headers

**CHN-11** `chain` MUST expose the calls of Table 3.2.2-1 with the stated behaviour.

Table 3.2.2-1. Header calls

| Call               | Input                                               | Output                                                                                                                                          |
|--------------------|-----------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------|
| `validate_headers` | headers in chain order, each extending the previous | `ok {first_height, last_height, last_chain_work}`, or `rejected {index, reason}`, or `not_connected` if the first header's parent is not stored |
| `store_headers`    | headers for which `validate_headers` returned `ok`  | stored, each with its height and chain work; `not_connected` if the first header's parent is not stored                                         |
| `header`           | block hash                                          | stored header entry `{header, height, chain_work, has_block}`, or not found; `has_block` is true when the block is in `blocks`                  |
| `header_at`        | height                                              | header entry of the active chain at that height, or not found                                                                                   |

**CHN-12** `validate_headers` MUST write nothing.

**CHN-13** `store_headers` MUST store the headers with their height and chain work in `headers`, in the order of
[STO-12](3.5-logical-database.md#storing-headers).

### Blocks

**CHN-14** `chain` MUST expose the calls of Table 3.2.2-2 with the stated behaviour.

Table 3.2.2-2. Block calls

| Call            | Input      | Output                          |
|-----------------|------------|---------------------------------|
| `connect_block` | block      | new tip, or `rejected {reason}` |
| `block`         | block hash | stored block, or not found      |

**CHN-15** `connect_block` MUST proceed as follows:

1. The block's header MUST be stored; otherwise the result is `rejected {unknown-header}`.
2. The block's parent MUST be the tip block; otherwise the result is `rejected {not-sequential}`.
3. The block is validated as in CHN-07 and CHN-08. If invalid, the result is `rejected {reason}` and nothing is
   written.
4. The block is stored, applied to the UTXO set, and the tip is moved to it, in the order of
   [STO-13](3.5-logical-database.md#connecting-a-block-to-the-tip-block).

### Tip and UTXO set

**CHN-16** `chain` MUST expose the calls of Table 3.2.2-3 with the stated behaviour.

Table 3.2.2-3. Tip and UTXO set calls

| Call             | Input    | Output                                                 |
|------------------|----------|--------------------------------------------------------|
| `tip`            | —        | `{hash, height, chain_work}` of the tip block          |
| `disconnect_tip` | —        | new tip                                                |
| `coin`           | outpoint | the unspent output (coin), or not found                |

**CHN-17** `disconnect_tip` MUST remove the outputs the tip block created from `coins`, restore the coins from the
block's `undo` entry, and move the tip to the block's parent, in the order of
[STO-14](3.5-logical-database.md#disconnecting-the-tip-block).

**CHN-18** `chain` MUST NOT disconnect the genesis block: `disconnect_tip` MUST fail when the tip is the genesis
block.

## Configuration

**CHN-19** `chain` MUST read the `[chain]` table with the keys of Table 3.2.2-4.

Table 3.2.2-4. `[chain]` configuration keys

| Key                    | Type         | Content                                       | Default |
|------------------------|--------------|-----------------------------------------------|---------|
| `chainstate_cache_mib` | integer, MiB | RocksDB block cache of the `chainstate` store | `512`   |
| `headers_cache_mib`    | integer, MiB | RocksDB block cache of the `headers` store    | `128`   |
| `blocks_cache_mib`     | integer, MiB | RocksDB block cache of the `blocks` store     | `128`   |

```toml
[chain]
chainstate_cache_mib = 512 # RocksDB block cache of the chainstate store
headers_cache_mib = 128    # RocksDB block cache of the headers store
blocks_cache_mib = 128     # RocksDB block cache of the blocks store
```
