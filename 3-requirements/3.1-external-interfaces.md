# 3.1 External interfaces

## 3.1.1 Peer-to-peer interface

Vakthund talks to Bitcoin peers over TCP using the Bitcoin P2P protocol with transport v1 framing [R12]. Peers are assumed
to behave as Bitcoin Core ([Appendix A](../5-appendices.md#a-assumptions-and-dependencies)).

**EXT-01** Vakthund MUST communicate with peers over TCP using the Bitcoin P2P protocol with transport v1 framing: a
message header of network magic (4 bytes), command (12 bytes), payload length (4 bytes) and checksum (4 bytes),
followed by the payload.

**EXT-02** Vakthund MUST NOT accept inbound TCP connections.

**EXT-03** Vakthund MUST use the network magic of the network selected by the `network` configuration key.

**EXT-04** Vakthund MUST treat a received message as invalid when its magic differs from the network magic, when its
checksum does not match its payload, or when its payload length exceeds 4 000 000 bytes (Bitcoin Core
`MAX_PROTOCOL_MESSAGE_LENGTH`). The reaction to an invalid message is [TBD-08].

**EXT-05** Vakthund MUST send only the commands marked as sent in Table 3.1-1.

**EXT-06** Vakthund MUST NOT act on a received message whose command is not listed in Table 3.1-1.

Table 3.1-1. Commands

| Command                                  | Direction                | Owner        | Reference                     |
|------------------------------------------|--------------------------|--------------|-------------------------------|
| `ping`                                   | sent, received           | `net`        | BIP31                         |
| `pong`                                   | sent, received           | `net`        | BIP31                         |
| commands of the connection flow          | sent, received           | `net`        | [TBD-02]                      |
| `getheaders`                             | sent; received [TBD-09]  | `block-sync` |                               |
| `getdata`                                | sent; received [TBD-09]  | `block-sync` | BIP144 (`MSG_WITNESS_BLOCK`)  |
| `headers`                                | received                 | `block-sync` |                               |
| `block`                                  | received                 | `block-sync` |                               |
| `inv`                                    | received                 | `block-sync` |                               |
| `notfound`                               | received [TBD-09]        | `block-sync` |                               |

## 3.1.2 Configuration file

**EXT-07** Vakthund MUST read its configuration from one TOML file [R19].

**EXT-08** The configuration MUST consist of the top-level keys of Table 3.1-2 and one table per module: `[net]`
([3.2.1](3.2.1-net.md#configuration)), `[chain]` ([3.2.2](3.2.2-chain.md#configuration)), `[block-sync]`
([3.2.3](3.2.3-block-sync.md#configuration)). Top-level keys apply to every module; each module reads its own table.

Table 3.1-2. Top-level configuration keys

| Key       | Type   | Values                                           | Default   |
|-----------|--------|--------------------------------------------------|-----------|
| `network` | string | `main`, `testnet4`, `signet`, `regtest`          | `main`    |
| `datadir` | path   | directory under which the stores are kept        | `~/.vakthund` |

```toml
network = "main"           # main | testnet4 | signet | regtest
datadir = "~/.vakthund"        # stores live under <datadir>/<network>/
```

## 3.1.3 Data directory

**EXT-09** Vakthund MUST keep every store under `<datadir>/<network>/`, at the paths given in
[Table 3.5-1](3.5-logical-database.md#stores).
