# 3.5 Logical database requirements

A **store** is the unit of atomicity: a set of tables written together in all-or-nothing updates. A **table** is a
key-value map inside a store.

**STO-01** A write to a store MUST be a batch: every table update of the batch is applied, or none is.

**STO-02** Data that MUST change atomically together MUST be in the same store.

**STO-03** Data that does not need to change atomically together MUST be kept in separate stores.

**STO-04** A store MUST belong to exactly one module.

**STO-05** There is no atomicity across stores. Consistency across stores MUST be ensured by the
[write ordering](#write-ordering).

## Stores

**STO-06** The stores of v0.1 MUST be those of Table 3.5-1.

Table 3.5-1. Stores

| Module | Store        | Tables                            | Path                                    |
|--------|--------------|-----------------------------------|-----------------------------------------|
| chain  | `chainstate` | `coins`, `undo`, `active`, `meta` | `<datadir>/<network>/chain/chainstate/` |
| chain  | `headers`    | `headers`                         | `<datadir>/<network>/chain/headers/`    |
| chain  | `blocks`     | `blocks`                          | `<datadir>/<network>/chain/blocks/`     |
| net    | `peer-list`  | `peer-list`                       | `<datadir>/<network>/net/peer-list/`    |

`block-sync` has no store. `headers` and `blocks` are separate stores: a block body and its header never need to
change together.

The "Profile" column of the table definitions below names the tuning profile of
[DES-08](3.6-design-constraints.md#engine).

### chainstate

**STO-07** The `chainstate` store MUST consist of the tables of Table 3.5-2. The UTXO set and the tip are in one store,
so a block is applied or reverted together with the tip move.

Table 3.5-2. `chainstate` tables

| Table    | Key        | Value                                                                                   | Profile      |
|----------|------------|-----------------------------------------------------------------------------------------|--------------|
| `coins`  | outpoint   | amount, scriptPubKey, height, coinbase flag                                             | point lookup |
| `undo`   | block hash | the coins the block spent (amount, scriptPubKey, height, coinbase flag), in input order | large values |
| `active` | height     | block hash, block time and median time past of the active chain at that height          | sequential   |
| `meta`   | `tip`      | block hash and height of the tip                                                        | —            |

### headers

**STO-08** The `headers` store MUST consist of the table of Table 3.5-3. Only valid headers MUST be stored in it.

Table 3.5-3. `headers` tables

| Table     | Key        | Value                                            | Profile      |
|-----------|------------|--------------------------------------------------|--------------|
| `headers` | block hash | header (80 bytes), height, cumulative chain work | point lookup |

### blocks

**STO-09** The `blocks` store MUST consist of the table of Table 3.5-4.

Table 3.5-4. `blocks` tables

| Table    | Key        | Value                                               | Profile      |
|----------|------------|-----------------------------------------------------|--------------|
| `blocks` | block hash | block in consensus encoding, including witness data | large values |

### peer-list

**STO-10** The `peer-list` store MUST consist of the table of Table 3.5-5.

Table 3.5-5. `peer-list` tables

| Table       | Key                      | Value                                                            | Profile      |
|-------------|--------------------------|------------------------------------------------------------------|--------------|
| `peer-list` | peer address (`ip:port`) | features recorded for the peer ([3.2.1](3.2.1-net.md#state))     | point lookup |

## Write ordering

Numbered steps MUST be performed in the given order; bulleted steps have no required order. Ordered steps are written
in sync mode ([DES-09](3.6-design-constraints.md#engine)).

### First start

**STO-11** On first start `chain` MUST write:

1. the genesis block to `blocks` and the genesis header to `headers`;
2. one `chainstate` batch that updates all involved tables (`meta`, `active`, `coins`, etc.).

### Storing headers

**STO-12** `chain` MUST write headers to `headers` in batches.

### Connecting a block to the tip block

**STO-13** To connect a block, `chain` MUST write:

1. the block to `blocks`;
2. one `chainstate` batch that:
    - saves the block's new outputs to `coins`;
    - removes the spent outputs from `coins` and creates the block's `undo` entry;
    - sets `active` at the block's height;
    - sets `meta.tip` to the block's hash and height.

### Disconnecting the tip block

**STO-14** To disconnect the tip block, `chain` MUST write one `chainstate` batch that:

- removes the outputs created by the block from `coins`;
- saves the outputs of the block's `undo` entry to `coins`;
- removes the block's `undo` entry;
- removes the block's height record from `active`;
- sets `meta.tip` to the parent's hash and height.

**STO-15** A disconnected block MUST stay in `blocks`.
